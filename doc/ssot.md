# WP Perf Shield SSOT

This file is the single source of truth for packaging and release conventions.

## Plugin Identity

- Plugin folder: `wp-perf-shield`
- Main plugin file: `wp-perf-shield.php`

- Author: `MENJ`

## Documentation Layout

The root must keep only the WordPress.org-compatible `readme.txt`.

Project documentation belongs in:

```text
doc/readme.md
doc/upgrading.md
doc/changelog.md
doc/ssot.md
```

The operator-facing manual smoke-test checklist lives in `doc/upgrading.md` under the "Manual Smoke-Test Checklist" heading. Run it on staging before publishing each release.

The operator-facing post-remediation cache invalidation checklist lives in `doc/upgrading.md` under the "Post-Remediation Cache Invalidation Checklist" heading. Run it on production after every remediation pass that removes confirmed malware artefacts. The checklist exists because cleanup at the WordPress layer does not flush every cache layer (object cache, page cache plugin, Plesk WP Toolkit cache, PHP OPcache, Nginx reverse proxy, CDN edge cache, browser cache, service worker cache) that may have stored a copy of the infected page. Without a deliberate cache invalidation pass, a fully-cleaned site can continue serving cached malicious HTML to visitors for hours.

## Indicator Data

Versioned malware indicator data lives in:

```text
includes/class-wps-indicators.php
```

`WPS_Indicators::INDICATOR_VERSION` should be bumped whenever the lists change. Hash lists, suffix patterns, and regex catalogues that are tightly coupled to specific scanner or hardening logic remain in their owning class until a parity-test harness exists.

## Auto-Delete Policy

Automatic deletion is reserved for confirmed malware evidence: exact malware
family folders, known malicious filenames or hashes, confirmed webshell/dropper
signatures, or multi-signal payloads that meet the scanner's own critical
threshold. Broad substrings, weak heuristics, harmless uploads `index.php`
silence stubs, active-theme critical files, and below-threshold payload scores
must stay review-only. Files that need modification rather than deletion must
be backed up with a timestamped non-overwriting backup before any write.

## Tooling

Pre-release validation is automated in:

```text
tools/verify-package.ps1
```

It runs the parser fallback on every PHP and admin JS file, asserts version-marker consistency across the four declared release files, checks the required directory layout, and refuses any stray markdown at the package root. Run it from the repo root before building the release ZIP.

## Admin Tab Layout

The admin tabs follow the incident-response workflow, grouped into an action band, an observability band, and a configuration band (regrouped in 1.3.66; the `logs` tab was added in 1.3.73):

```text
Overview -> Forensics -> Remediation -> Hardening -> Diagnostics -> Events -> Logs -> Settings
```

`$tab_group_starts` marks the first tab of the observability band (`diagnostics`) and the configuration band (`settings`).

Backward-compatible aliases should continue to resolve:

```text
dashboard -> overview
analytics -> diagnostics
log -> events
```

Operational telemetry such as hostile IP blocks belongs in Diagnostics. The Logs tab is read-only server access/error-log inspection (campaign-indicator scan and the automated-login signature) and must never expose a path parameter that escapes the code-defined, allow-listed log roots. Settings should stay focused on custom indicators, behavior toggles, and danger-zone maintenance actions.

The Diagnostics tab owns the Source Trace panel. Source Trace should correlate retained security events, active hostile IP blocks, cached scan findings, cached Forensics artifacts, and trace-focused SSH grep commands without running new heavy scans on normal page load. If the cached Forensics report is missing, the panel should say so and still render event/IP evidence.

Database option rows in Source Trace must be described carefully. WordPress `wp_options` has no native creation timestamp, so option anomalies should be shown at Forensics report time unless a scan, cleanup, or event log row captured a more precise time.

Hardening tab AJAX feedback should use compact status badges rather than raw inline text next to action buttons. Successful one-way Apply actions may hide the original button until the page reloads and the persisted state is rendered.

Removing `.htaccess` hardening rules must delete the whole WordPress marker block, not leave an empty marker pair. Status checks should verify expected rule lines, not only marker headers.

Each hardening action must have only one status target ID. Avoid standalone hidden status elements that duplicate the generated `*-msg` badge ID, because inline `display:none` can hide AJAX success feedback.

## Upload Pathway Protection

Blocked malware upload events should preserve enough context to trace the pathway:

- request route / URI
- request method
- AJAX action
- REST route
- referrer
- current WordPress user and roles
- upload, plugin-install, and manage-options capability state

ZIP uploads are restricted by default to trusted administrator WordPress upload routes. Unsafe front-end, REST, custom `admin-ajax.php`, file-manager, or unauthenticated ZIP upload pathways should be blocked and logged as `upload_path_blocked`.

All ZIP uploads, including trusted administrator routes, should still be inspected for known malware content before acceptance. The ZIP content guard should check entry names, known suffix patterns, built-in/custom PHP hashes, and high-confidence campaign payload markers.

WP Perf Shield release ZIPs are a special false-positive case because the plugin source legitimately contains malware indicators. A self-package exemption must stay narrow: only a valid `wp-perf-shield/` package with the real main plugin file may ignore indicator strings in known WP Perf Shield PHP files, and unknown extra PHP files inside that package must still be inspected.

### On-chain (EtherHiding) and obfuscated-loader detection

Recent variants no longer rely only on a plain C2. Two detection layers cover the evolution:

- **EtherHiding.** `WPS_Indicators::etherhiding_indicators()` lists the public Binance Smart Chain and Polygon JSON-RPC hosts plus the `eth_call` / `eth_getStorageAt` read primitives. `check_clickfix_c2_in_options()` flags a decoded `wp_<10hex>_cfg` payload that fetches its next stage from an on-chain contract. The rembat.my sample read its stage from a Polygon contract (`0x08207B087F61d7e95E441E15fd6d40BEfd6eD308`, selector `0x38bcdc1c`) and set dismissal cookies `_cf_verified` and `_wp_perf_ok`.
- **Self-decoding loader.** `check_obfuscated_loader()` detects the XOR-plus-base64 loader by structure (a base64 blob, a `charCodeAt(...)^key` loop, a TextDecoder/fromCharCode pass, and a `new Function()`/`eval()` sink), then base64-decodes and brute-forces the single-byte XOR to recover the payload, key, contract, and chain hosts. Structure-based matching is required because literal signatures keyed to one sample's variable names are defeated by per-variant name randomisation and XOR-key rotation (keys 84, 113, 114, 179 seen to date).

## Confirmed RAT Placement

The confirmed second-stage RAT/backdoor family may also hide outside normal plugin folders. Built-in checks should cover:


## wp-config.php Cleanup

`wp-config.php` cleanup must stay targeted and reversible:

- detect only known removable executable payloads, suspicious local/remote includes, option-loader restorers, and campaign markers
- create a backup before writing
- use atomic temp-file replacement
- refuse to write if the cleaned result fails sanity checks for `DB_NAME`, `DB_USER`, `ABSPATH`, and `wp-settings.php`
- update the stored clean baseline only after a successful cleanup
- log what was removed

A plain hash mismatch is not enough to clean automatically. If no removable pattern is found, the operator must review the file manually or reset the baseline only after confirming the edit was intentional.

### Public-disclosure decision (1.3.60)

A protocol-compliance audit at 1.3.60 found that all five victim-site domain names were named explicitly across the four public-facing documentation files. The protocol's `public-disclosure-guidance` section advises against publishing customer data and private production paths in public docs. The named domains are the operator's own sites, so the strict customer-data definition does not apply, but the explicit listing publishes a connection between the operator's network and a malware compromise.

The decision recorded here is to redact the public-facing documentation files (positional references replace explicit domain names) while keeping the domain literals in code where they are functionally required (`WPS_Indicators::known_rat_victim_sites()` for XOR-seed lookup) and in inline source comments adjacent to per-victim hash entries (technical annotations operators see when reading the code, not public-facing prose). The forensic insights, timing context, and detection capability are preserved across the redaction; only the identification of the specific operator's network is removed from public surfaces.

This decision applies prospectively to all future releases. Public documentation files refer to the catalogued victim sites by position only. Code files retain the literal domain values and the explanatory comment block that documents why they are present.

### Post-1.3.57 incremental updates

Versions 1.3.58 and 1.3.59 are not formal protocol re-audits; they are incremental IoC catalogue and detection-capability updates that ship between formal audit cycles. The protocol's `release-checklist` requirements (version markers, changelog entry, upgrading entry, readme update, ssot update, regression tests where applicable) apply to these incremental releases. The protocol's full vulnerability-checks methodology is not re-run on every incremental release  it is re-run when the codebase changes substantively enough to warrant it, or on a calendar cadence the operator chooses.

**1.3.58** added two changes. First, specific catch for a new ClickFix variant `auto-content-profiler-0b8d.php` that used a previously-unseen variable-concatenation evasion technique. Slug, hash, suffix pattern, DB option key, and class-name signature all added to the per-prefix detection layer. Second, a new generic shape-based detector `WPS_Scanner::check_clickfix_shape_heuristic()` that recognises any fake-plugin-folder ClickFix variant by structural traits rather than per-prefix string matching: single-file shape, file size 5-15 KB, `developer.wordpress.org/plugins/` Plugin URI, hex-suffix class name, `wp_<10hex>_cfg` option literal, late-priority `add_action`. Score 5-6 = high severity auto_delete, score 4 = high review-only, score 3 = medium review-only. The shape heuristic raises the operator's cost: rotating prefixes no longer evades detection because the heuristic does not depend on the prefix at all. 12/12 behavioural test assertions passed across both per-prefix and heuristic layers.

**1.3.65** is a bug-fix release for the inline "Delete this path" button on Overview findings. The button was added in 1.3.61 and described as working in that release's changelog, but operator inspection on 8 May 2026 surfaced that clicking it did nothing  no AJAX call, no error, no feedback. Independent inspection of the rendered HTML found the cause: the 1.3.61 PHP template interpolated `wp_json_encode()` output directly into a double-quoted onclick attribute. The JSON-encoded values contain double-quote string delimiters, which closed the outer onclick attribute prematurely. The browser parsed the rendered onclick as `wpsForensicAct(this, 'wps_delete_file', { path: ` (truncated at the first inner double-quote) and treated everything after as separate, malformed HTML. The click handler was never installed. The button has been silently inert across four releases (1.3.61, 1.3.62, 1.3.63, 1.3.64) because none of the intervening releases re-rendered the affected component or verified the resulting HTML parsed as intended. The fix matches the working pattern used by the Forensics-tab `forensic_action_button()` helper since 1.3.x: build the onclick JS expression as a single PHP string, then pass it through `esc_attr()` before placing it into the rendered HTML. `esc_attr()` converts inner `"` to `&quot;`, which the browser HTML-decodes back to `"` when populating the JS engine's argument list. End-to-end test simulating the full pipeline (PHP template render → browser HTML-attribute extraction → JS engine argument parse) passes 4/4 across the operator-reported `seo-by-rank-math/vendor/donatj/phpuseragentparser/.helpers` path and three additional cases covering apostrophe and ampersand edge cases. This is the second consecutive release shipping a feature that did not work as documented (the 1.3.63 → 1.3.64 sequence had the same shape: design intent recorded, feature shipped, regression caught after operator inspection, fix in the next release). Two consecutive instances of this pattern is not coincidence  it is the absence of an end-to-end verification step in the release-checklist. For releases that modify rendered admin UI from this point forward, the release-checklist adds three new steps: (1) render the affected component to a static HTML string in a PHP test harness, (2) extract the rendered attribute or text in question and confirm it parses as the intended structure, (3) for interactive elements with onclick or similar handlers, confirm the JS-engine-visible argument list matches the intended values after the browser performs its HTML-decoding pass. This section is the authoritative sequencing for everything queued after 1.3.97. It merges three inputs: the Tier-2 detection backlog, the security-hardening audit (triaged 2026-07-02), and the EDR product roadmap (adopted 2026-07-03). The positioning shift is deliberate and approved: WP Perf Shield grows from a purpose-built anti-malware scanner into a WordPress EDR platform that detects attacker behaviour, correlates events into incidents, and explains what happened. Signature scanning stays; behavioural detection joins it.

### The one-schema rule

The hardening audit's immutable HMAC-chained log and the roadmap's enriched event record are the same subsystem, and it gets built once. The current logger (`includes/class-logger.php`) writes a four-field event - time, type, subject, ip - capped at 200 entries in a JSON file. Its replacement is designed to the full unified schema from day one, even though early releases populate only part of it:

```text
timestamp, event_type, username, user_role, user_id, session_id,
incident_id, correlation_id, ip, country, city, asn, user_agent,
referer, request_uri, object_type, object_name, action, severity,
risk_score, notes, previous_hash, current_hash, hmac_signature
```

Fields the plugin can't populate yet (country/city/asn before the GeoIP decision; incident_id before correlation ships) are stored null rather than omitted, so the record shape never changes underneath consumers. `WPS_Logger::log_event()` stays as a shim that writes a schema-shaped record with the fields it has, so all ~70 existing call sites keep working unmodified.

### Release train

**1.3.98 - Tier-2 detection.** Verify-then-rescan after removal, the unified C2 content sweep, functions.php redirect-injection detection, and the per-scan wall-clock budget. Small, self-contained, keeps detection momentum while the event-subsystem design settles. No architectural risk.

**1.3.99 - Hardening I: the event subsystem.** New `WPS_Event_Log` implementing the unified schema with an HMAC-chained record (previous_hash + current_hash + hmac_signature per the audit), tamper-evident verification, secure storage (randomised filename, deny-PHP/deny-listing rules, rotation), and migration of the existing 200-entry log. Events tab re-rendered from the new store. The old `log_event()` API survives as the shim described above. Storage engine (custom table versus append-only secured file) is Decision 4 below and gets settled before this release starts.

**1.4.0 - Hardening II: complete the audit's high-priority list.** Rate limiting on destructive actions (delete, quarantine restore/purge, cleanup, salt regeneration; 30s cooldown, per-user), per-action audit enrichment (initiating user, original value, new value, reason, risk level - the quarantine manifest's `stored_by`/`reason` fields from 1.3.97 are the pattern, generalised), plugin self-baseline integrity (sha256 baseline of the plugin's own files at install/upgrade, verified on admin load and scheduled scans - distinct from the 1.3.89 wordpress.org check, which covers other plugins), and signed diagnostic exports. The 1.4.0 number marks the platform foundation as complete. Deferred from the audit as low-leverage: the AuthorizationManager formalisation (guard_request already centralises nonce + capability), the Request/Validator/Controller split, and REST hardening (the plugin registers no REST routes; re-evaluate if that changes).

**1.4.1 - EDR Phase 1: sessions, incidents, risk.** The plugin registers its first behavioural hooks: `wp_login`, `wp_logout`, `user_register`, `current_screen`, plus upload/activation/editor interceptors. Login timeline reconstruction per administrator session; incident grouping by session, IP, user, and a configurable time window; cumulative risk scoring against the adopted score table (successful login 10 -> new admin account 120, severity bands low 0-50 / medium 51-120 / high 121-220 / critical 221+, Decision 5 below); a timeline card in the admin. GeoIP-dependent scores (first-seen country, impossible travel) stay dormant until Decision 1.

**1.4.2 - EDR Phase 2: behaviour baselines.** Login history with trusted devices (mark/revoke), administrator behaviour baseline (pages, hours, IPs, browsers) with anomaly alerts, impossible travel (gated on Decision 1), session fingerprinting against cookie theft (gated on Decision 2).

**1.4.3 - EDR Phase 3: integrity and session summaries.** Proper file-integrity monitoring over the defined set (wp-config.php, .htaccess, mu-plugins, active theme, plugins, functions.php; sha256; triggered on login/logout/scheduled scan; reports modified/added/deleted) - this generalises the existing wp-config baseline and redrop hashing into one FIM. Admin session summary on logout. Event-time persistence detection (new-admin-account alerts via `user_register`, option-change monitoring) complementing the seven scan-time persistence checks that already ship (cron tampering, mu-plugins, wp-config, auto-prepend, dropins, dropper persistence, base64 options).

**1.4.4 - EDR Phase 4: classification.** Attack categorisation (brute force, credential stuffing, session hijacking, privilege escalation, persistence, reconnaissance, malware execution), the plugin-installation-chain correlator, admin-recon classification, and MITRE ATT&CK mapping as a static technique table over existing and new detections (T1110 brute force, T1505.003 web shell, T1078 valid accounts, extended as detections map). The Apache/Nginx log correlation from the optional server features slots here: `WPS_Log_Reader` (1.3.92) already greps readable logs in PHP; correlation joins those lines to events by timestamp + IP.

**1.4.5 - EDR Phase 5: visualisation.** Interactive filterable timeline, incident replay as a chronological narrative, one-page executive summary per critical incident. The incident graph ships only if it earns its complexity over the timeline view.

**Phase 6 (deception) - parked.** Honeypot admin accounts write to the users table and the honey-plugin endpoint accepts uploads by design; both change the plugin's risk posture and neither proceeds without explicit item-level approval (Decision 3).

### Decisions requiring explicit approval before their release

1. **GeoIP source** (blocks impossible travel, first-seen-country scoring, country/city/asn enrichment). Options: bundle MaxMind GeoLite2 (licence terms, update mechanism, tens of MB on disk), call an external lookup API (the plugin currently makes no third-party calls and works on restricted hosting - this reverses that posture), or ship without (fields stay null, dependent detections stay dormant). Default until decided: ship without.
2. **Client-side fingerprinting** requires JS collection on wp-admin pages beyond the plugin's own screens (admin.js currently loads only there) plus storage of per-session fingerprints. Default until decided: dormant.
3. **Deception features** (users-table writes, decoy upload endpoint). Default: parked.
4. **Event storage engine** - RESOLVED 1.3.99: custom DB table (`{$prefix}wps_events`). Phase-1 incident grouping is query-shaped work, the HMAC chain supplies tamper evidence either way, and a table survives filesystem resets; wholesale truncation is covered by the dual chain anchors. (Original options: table versus append-only secured file.)
5. **Risk score table**: adopt the roadmap's values as shipped defaults or recalibrate after 1.4.1's timeline data exists. Scores ship as filterable constants either way, in one place, per the one-source-of-truth rule.

### Standing rules extended to the programme

Detection remains technique-first; behavioural alerts follow the same review-only versus auto-remediation discipline as file detections (an anomaly is never auto-remediated; only content-confirmed malware is). Every list - scores, MITRE mappings, tracked screens, FIM file sets - lives in exactly one constant with accessors. UI additions follow the token system (PHP chooses classes, CSS owns colours, value-preserving) and the tabbed layout. The verification protocol extends to hook-driven features: the fixture harness gains WordPress hook stubs (`add_action`/`do_action` capture) so timelines and scoring are testable the way 1.3.97's detections are, and changelog claims stay grounded in what the harness actually exercised. `INDICATOR_VERSION` is unaffected by any of this planning; it moves only when the indicator lists change.
